The documented cross-account "become a client" mode can never succeed. probePortHolder classifies the port holder as ours only when readInstanceToken returns a token matching the one the running server serves — but with per-user roots the second account never has the first account's token, and in shared-cache mode writeInstanceToken creates the token 0600, so a peer account's read fails EACCES. Either way the probe returns holderForeign, acquireListener errors, and main exits 1 with an impersonation warning; only a same-account relaunch reaches client mode. Aggravation in shared mode: the root's sticky bit blocks os.Rename over a token owned by another account, so once account B has run the server, account A's stale-token cleanup fails and even A's own live server is classified foreign. The decisions record ("one server, one GPU, N user accounts") and the main.go package doc promise the opposite.

Fix needs a design decision, so it is deferred rather than auto-patched: making the token group-readable would let any local account impersonate the server (reading the token is all a squatter needs to answer the probe), defeating the 0600 anti-forgery choice. A sounder shape is a same-root proof that keeps no shared secret at rest — e.g. the prober drops a random nonce file into the root and asks the server over loopback to echo it back — plus EPERM-tolerant cleanup of stale tokens. Documenting client mode as same-account-only would also resolve the contradiction, at the cost of the feature.

Scope note (2026-07-30, bug-hunt round 4 verification): the "0600 anti-forgery" premise this issue rests on is already defeated in the *default per-user configuration*, independently of file permissions. The live server publishes its instance token to every loopback caller via `GET /api/instance` (internal/gateway/control.go:71-73, mounted on the loopback-only control plane whose own comment concedes it is reachable by "other user accounts, which reach it over 127.0.0.1"). So a second local account B can read account A's token over HTTP even though the file is 0600 and unreadable to B. That does not rescue the benign client mode above (probePortHolder still compares the served token against B's *own* root token, which differs — the holderForeign path still fires), but it opens the reverse hazard: an *impersonation*. B harvests T from `/api/instance` while A runs, waits for A to quit (nothing deletes `instance.token` on shutdown, so A's on-disk T persists), squats the port serving T, and on A's next relaunch A's probe — which reads the stale on-disk T *before* runServer writes a fresh token (main.go:81 acquireListener precedes main.go:147 writeInstanceToken, and runServer is only entered when the port is claimed) — matches B's replayed T, returns holderOurs, and A silently runs as a client of B, routing A's model prompts/completions through B. Fail-open, unlike iss-5's fail-closed direction. No safe minimal patch exists: `/api/instance` cannot simply be removed because probePortHolder/fetchInstanceToken require the holder to disclose the token over loopback for the scheme to work at all; the only sound fix is the same nonce challenge-response redesign proposed above, which keeps no replayable secret at rest or on the wire. This corrects this issue's original claim that "the second account never has the first account's token" — via the HTTP endpoint it does — and folds the impersonation vector into the same deferred design decision.
